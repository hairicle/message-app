# 4 — API reference

Every route is listed. This was generated by reading the controllers, so it matches what is
deployed rather than what was designed.

**Completeness, so it can be re-checked after a change:** 84 HTTP routes, 13 events a client may
send, 18 a client may receive. To re-derive the HTTP count from a checkout:

```bash
grep -rhoE "@(Get|Post|Put|Patch|Delete)\(" apps/api/src --include='*.controller.ts' | wc -l
```

## Conventions

- **Base path:** every route is prefixed `/api`, **except `GET /health`**, which is deliberately at
  the root so a load balancer's health check does not need to know about the prefix.
- **Auth:** `Authorization: Bearer <token>` on everything except `GET /health`,
  `POST /api/auth/login` and `POST /api/auth/login/totp`.
- **Errors:** always `{ "error": "message" }`. Validation failures add
  `fields: [{ field, message }]`.
- **Rate limiting:** configured (100 requests / 60 s) but **not currently enforced** — see
  [Known gaps](05-deployment.md#known-gaps-read-before-going-live).

### Status codes you will see

| Code | Meaning here |
|---|---|
| 400 | Malformed body, an identifier that is not a UUID, or a rule violation (group too small, file too large) |
| 401 | Missing, expired or half-authenticated token |
| 403 | Authenticated but not permitted — not a member, or not an admin. Also a disabled account. |
| 404 | Not found, or found but not visible to you |
| 500 | Genuine server fault. These are logged; a 400-class mistake is not. |

## Conversations — `/api/conversations`

| Method | Path | Auth | Body / notes |
|---|---|---|---|
| GET | `/` | yes | Your conversations, pinned first |
| POST | `/` | yes | `{ type: 'direct' \| 'group', name?, description?, memberIds[], teamId? }` |
| GET | `/:id` | member | One conversation with its members |
| PATCH | `/:id` | owner/admin | `{ name?, description? }` |
| POST | `/:id/avatar` | owner/admin | multipart, field `avatar`, max 5 MB. Rejected on direct conversations. |
| POST | `/:id/members` | owner/admin | `{ userIds: string[] }` |
| DELETE | `/:id/members/:userId` | see notes | Removing **yourself** is leaving and always allowed; removing anyone else needs owner or admin |
| GET | `/:id/media` | member | Images and video for the gallery |
| GET | `/:id/attachments` | member | `?types=file,audio` — comma-separated, defaults to `file` |
| GET | `/:id/pins` | member | Pinned messages in this conversation |
| POST | `/:id/pins` | member | `{ messageId }` |
| DELETE | `/:id/pins/:messageId` | member | |
| POST | `/:id/pin` | member | `{ pinned?: boolean }` — pins the **conversation** in your sidebar, defaults to `true` |
| POST | `/:id/mute` | member | `{ until: ISO-8601 \| null }` — `null` unmutes |
| PUT | `/:id/mute` | member | Mute indefinitely |
| DELETE | `/:id/mute` | member | Unmute |

> `POST /:id/pin` pins the conversation; `POST /:id/pins` pins a message inside it. Singular and
> plural mean different things — a genuine trap when writing scripts against this API.

**Group creation rules**, enforced server-side: a group needs a non-empty name and at least **3**
members including the creator. Duplicate ids in `memberIds` are stripped before the count.

## Messages — `/api/messages`

Static sub-routes are declared before `/:id` so they are not shadowed. Keep that ordering if you
add any.

| Method | Path | Auth | Body / notes |
|---|---|---|---|
| GET | `/search` | yes | `?q=…&conversationId=…` → `{ results, total, query }` |
| GET | `/pinned` | member | `?conversationId=…` |
| GET | `/bookmarks` | yes | `?conversationId=…` (optional) |
| GET | `/undelivered` | yes | Messages that arrived while you were offline |
| GET | `/` | member | `?conversationId=…&before=<id>&limit=50` |
| POST | `/` | member | `{ conversationId, type?, ciphertext?, replyToMessageId?, fileId? }` |
| PATCH | `/:id` | author | `{ ciphertext }` |
| DELETE | `/:id` | **admin only** | Soft delete. The row survives and renders as "deleted", but `ciphertext` is blanked, so the text is unrecoverable. Not even the author can delete their own message; the UI hides the button for non-admins. |
| POST | `/:id/read` | member | Marks read up to this message |
| POST | `/:id/reactions` | member | `{ emoji }` |
| DELETE | `/:id/reactions/:emoji` | member | URL-encode the emoji |
| POST | `/:id/pin` · DELETE | member | Pin/unpin a message |
| POST | `/:id/bookmark` · DELETE | member | Personal bookmark, private to you |
| POST | `/:id/forward` | member | `{ targetConversationId }` — carries the attachment across |

`type` is one of `text`, `image`, `video`, `audio`, `file`.

> **`ciphertext` is not encrypted.** Despite the name it holds base64-encoded plaintext in a `bytea`
> column. Search decodes before comparing — comparing against the stored base64 was a real bug and
> made search silently return nothing.

## Routable but not exposed in the UI

These work and are reachable by anyone with a token. They belong to unshipped phases, so they are
untested in practice and should be treated as an attack surface you may want to block at the edge
until their features ship.

**Teams** — `GET /api/teams`, `POST /api/teams`, `GET|POST /api/teams/:id/members`,
`DELETE /api/teams/:id/members/:userId`, `GET|POST /api/teams/:id/messages`,
`GET /api/teams/:id/pinned`

**Tasks** — `GET /api/tasks`, `POST /api/tasks`, `PATCH /api/tasks/:id`, `DELETE /api/tasks/:id`

**Meetings** — `GET /api/meetings`, `POST /api/meetings`, `DELETE /api/meetings/:id`

**Calls** — `GET /api/calls`, `POST /api/calls`, `DELETE /api/calls/:id`. These record call history
only; signalling is over the socket.

> **The call UI exists and is broken.** Buttons are visible in every conversation header, the client
> speaks a different socket protocol from the gateway, and pressing one turns the microphone and
> camera on without ever releasing them. No `RTCPeerConnection` is ever created and no TURN/STUN
> server is configured. See [G1 in the gaps register](06-gaps.md#g1-the-audio-and-video-call-buttons-do-not-work-and-leave-the-camera-on)
> — these buttons should be hidden before production.

# WebSocket API

Socket.IO, same origin and port as the API. The token goes in the handshake:

```js
io(API_URL, { auth: { token } })
```

An invalid, expired, TOTP-pending or disabled-account token causes an immediate disconnect rather
than an error event.

## Client → server

| Event | Payload | Notes |
|---|---|---|
| `message:send` | `{ conversationId, type?, ciphertext?, replyToMessageId?, fileId? }` | Client uses a 12 s ack timeout and falls back to HTTP |
| `message:edit` | `{ messageId, ciphertext }` | |
| `message:delete` | `{ messageId }` | |
| `message:read` | `{ messageId }` | |
| `message:react` | `{ messageId, emoji }` | |
| `message:unreact` | `{ messageId, emoji }` | |
| `typing:start` / `typing:stop` | `{ conversationId }` | Relayed to the room, excluding sender |
| `presence:get` | — | Replies with `presence:snapshot` |
| `call:offer` / `call:answer` / `call:ice-candidate` / `call:reject` | `{ targetUserId, … }` | Relayed to `user:<targetUserId>` |

## Server → client

| Event | Delivered to | Meaning |
|---|---|---|
| `message:new` | `conversation:<id>` | A message was created by any transport |
| `message:edited` | `conversation:<id>` | |
| `message:deleted` | `conversation:<id>` | |
| `message:read` | `conversation:<id>` | Read receipt |
| `reaction:added` / `reaction:removed` | `conversation:<id>` | |
| `conversation:new` | `user:<id>` | You were added to, or created, a conversation |
| `conversation:members-changed` | `conversation:<id>` | |
| `conversation:removed` | `user:<id>` | You were removed or left |
| `presence:update` | broadcast | `{ userId, status }` |
| `presence:snapshot` | requester | Reply to `presence:get` |
| `typing:start` / `typing:stop` | `conversation:<id>` | |
| `call:offer` / `call:answer` / `call:ice-candidate` / `call:reject` | `user:<targetUserId>` | The same four names arrive inbound as well as going out — the gateway relays each one to the target's user room, with the sender's id attached. A client has to listen for them, not only emit them. |
| `account:disabled` | `user:<id>` | Sent just before the socket is force-closed |

## Smoke test

The fastest end-to-end check after a deploy — it exercises auth, the database, the socket and
storage in four steps:

```bash
API=https://your-api-host

curl -sf $API/health                                             # 1. reachable

TOKEN=$(curl -sf -X POST $API/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@company.com","password":"…"}' | jq -r .token)

curl -sf $API/api/conversations -H "Authorization: Bearer $TOKEN" # 2. auth + database
curl -sf $API/api/users/directory -H "Authorization: Bearer $TOKEN"
```

Steps 3 and 4 need a browser: send a message and confirm it appears in a second tab **without a
reload** (proves the socket), then send an image and confirm it renders (proves storage and signed
URLs). The socket check is the one that catches a wrong `NEXT_PUBLIC_API_URL` — HTTP can appear
fine while the socket fails.
