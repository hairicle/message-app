# Staging deployment

Staging runs on [Render](https://render.com), both apps built from the Dockerfiles already in the
repo. `render.yaml` describes the environment; `.github/workflows/deploy-staging.yml` decides when
it ships.

Nothing deploys automatically on push. Render's own auto-deploy is off, and the workflow triggers a
deploy only after the build and all 134 tests pass — so a broken commit stops at CI rather than
becoming a broken staging environment.

---

## One-time setup

### 1. Create the services

In Render: **New → Blueprint**, point it at this repository and the `staging` branch. It reads
`render.yaml` and creates two services:

| Service | Source | Notes |
|---|---|---|
| `messenger-api-staging` | `apps/api/Dockerfile` | health check on `/health` |
| `messenger-web-staging` | `apps/web/Dockerfile` | binds the port Render assigns |

### 2. Set the secrets Render needs

Every variable marked `sync: false` in `render.yaml` has to be filled in before the first deploy.
They are not in the repo on purpose.

| Variable | Where it comes from |
|---|---|
| `DATABASE_URL` | Staging Supabase → pooled connection string (`:6543`, `?pgbouncer=true`) |
| `DIRECT_URL` | Staging Supabase → direct connection (`:5432`) **plus** `?sslmode=verify-full&sslrootcert=./certs/supabase-prod-ca-2021.crt` |
| `SUPABASE_SERVICE_KEY` | Staging Supabase → service role key |
| `STORAGE_ENDPOINT` | `https://<project-ref>.supabase.co/storage/v1/s3` |
| `REDIS_URL` | A staging Upstash database (`rediss://…`) |

`JWT_SECRET` is generated by Render. Do not paste the production one in.

**Use a separate Supabase project.** Pointing staging at production means test accounts, test
messages and any destructive experiment land in real data.

### 3. Add the deploy hooks to GitHub

Each Render service has **Settings → Deploy Hook**, a URL that triggers one deploy. Add both under
**GitHub → Settings → Secrets and variables → Actions**:

| Secret | Value |
|---|---|
| `RENDER_DEPLOY_HOOK_API` | deploy hook URL for `messenger-api-staging` |
| `RENDER_DEPLOY_HOOK_WEB` | deploy hook URL for `messenger-web-staging` |

Hooks rather than an API key: a hook can only redeploy the one service it belongs to, so a leak
cannot read or change anything else in the account.

### 4. Apply the schema

The staging database starts empty. From a machine with the staging `DIRECT_URL`:

```bash
cd apps/api
DIRECT_URL="<staging direct url>" npx prisma migrate deploy
```

This applies `prisma/migrations`, including the baseline. It does **not** run against production
unless you point it there, so check the URL before running it.

### 5. Create the first admin

There is currently no seed script — the NestJS refactor dropped the old `seed-admin`, so a fresh
database has no way to log in. Until one exists, insert the first user by hand:

```sql
INSERT INTO users (email, username, display_name, password_hash, role, status)
VALUES ('admin@company.local', 'admin', 'Admin', '<bcrypt hash, cost 12>', 'admin', 'active');
```

## Deploying

Merge into `staging` and push:

```bash
git checkout staging
git merge --ff-only develop
git push origin staging
```

The workflow type-checks both apps, runs both test suites, builds both, and only then calls the
deploy hooks. **Actions → Deploy staging** also has a manual trigger.

## Things worth knowing

**`NEXT_PUBLIC_API_URL` is baked in at build time.** Next inlines `NEXT_PUBLIC_*` during
`next build`, so the web image is tied to whichever API URL it was built with. Changing it at
runtime does nothing — the web service has to be rebuilt. `render.yaml` wires it from the API
service so this is handled, but it is the usual cause of a staging web app calling `localhost:4000`.

**The browser talks to the API directly, not through Next.** `SocketContext` opens the Socket.IO
connection against `NEXT_PUBLIC_API_URL`. That is deliberate: Next rewrites do not proxy WebSocket
upgrades in production, so routing the socket through the web service would break realtime
messaging. It also means the API must allow the web origin — `CORS_ORIGIN` is wired from the web
service for that reason.

**Free instances sleep when idle.** The first request after a quiet period takes a few seconds
while the container starts. Fine for staging; not for production.

**Storage buckets stay private.** Attachments and avatars are served through short-lived signed
URLs. A new Supabase project creates buckets as public by default — set `messenger-files` and
`avatars` to private, or staging will hand out permanent public links.
